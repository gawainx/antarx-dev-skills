# AGENTS

## 开发纪律

### 开发工作流

本项目使用如下流程。除非用户明确指定其他流程，需求开发按需求编号推进；simple 版本只简化文档落点，不简化开发流程。

1. 为每个需求分配递增编号，格式为 `REQ-NNNN`；创建新需求前必须检查 `docs/requirements/index.md` 和已有需求文件，使用当前最大编号加一。
2. 新需求先在 `docs/requirements/index.md` 登记编号、标题和状态。
3. 需求文件统一放在 `docs/requirements/`，文件名默认使用 `REQ-NNNN-short-title.md`，其中 `REQ-NNNN` 必须替换为实际递增编号。
4. 需求澄清、功能设计、开发计划、执行状态、验证结果和验收记录写在同一个需求文件中。
5. 需求澄清：优先复用用户已提供或已确认的结论，仅对影响范围、方案或验收标准的实质缺口与用户讨论。按实际需要和触发条件选择澄清技能；没有适用技能时直接完成澄清。范围和验收标准明确、没有阻碍下一阶段的未决问题时，视为澄清完成；此前禁止进入功能设计、开发计划或实现。
6. 功能设计：基于需求澄清结果完成方案设计，必要时和用户交互完成方案决策，写入同一需求文件的“设计文档”章节，写入后提醒用户审阅。设计文档禁止堆砌代码；涉及接口设计、字段设计等内容时，以表格形式清晰说明即可，必要时可使用函数签名，但不要列举代码实现。
7. 开发计划：根据功能设计制定执行计划，写入同一需求文件的“开发计划”章节，提醒用户审核修改。开发计划必须根据工作量划分为不同 Stage，并在 Stage 下根据必要性划分 Task。
8. 开发实现：根据开发计划进行开发，并持续更新需求文件中的任务状态、关键决策、验证命令和验证结果。完成每个 Stage 后，如果修改了任何代码，必须进行一次 git 提交。
9. 用户验收：用户验证通过后，在需求文件中标记完成，写入“验收与归档”，并更新需求索引和 `docs/PROGRESS.md`。未经用户允许，不自动归档、删除需求文件或覆盖已确认的范围、设计决策和验收结论；已授权开发中的任务状态、关键决策和验证记录应持续更新，无需逐次确认。
10. 所有文档使用 Markdown 格式撰写，语言为简体中文，关键术语、函数接口等信息可保留英文。自然段保持连续，不为控制行宽或适配编辑器插入硬换行；列表、表格、代码块、引用块及语义上确需换行的内容除外。

### 编码纪律

1. 代码优先保持简单、清晰、可维护；避免过度抽象和无必要的兼容层。
2. 新增类、函数或模块前，先搜索现有实现；能复用、扩展或合并时，不重复造功能相似的代码。
3. 命名必须表达业务含义；禁止使用含糊缩写、临时命名或与实际职责不符的名称。
4. 函数、类和模块都应保持单一职责；复杂逻辑先拆分为清晰步骤，再实现细节。
5. 避免巨型类和巨型文件；当一个文件承担多个职责时，按领域、层次或复用边界拆分模块。
6. 模块边界要清晰：公共接口稳定、内部实现内聚，避免跨模块散弹修改。
7. 注释只解释意图、约束和非显而易见的取舍；公共类、公共函数按项目语言的 docstring 规范补充说明。
8. 日志只记录关键流程、异常分支和重要状态变化；合理区分日志级别，避免输出敏感信息。
9. 异常处理必须有明确目的：能恢复则恢复，不能恢复则携带上下文向上抛出；禁止吞掉异常。
10. 修改代码时同步更新相关测试、文档、配置和调用方；不顺手重构无关代码。
11. 提交前至少运行与本次修改相关的格式化、静态检查或测试，并记录验证结果。

## 初始化规则

- 初始化命令只创建缺失目录和文件。
- 初始化脚本跳过已存在的普通文件和目录；已有 AGENTS.md 与模板不同时只报告 DIFF，不覆盖、追加或合并。禁止通过脚本删除、重命名或改写已有内容。
- 已授权初始化时，agent 按 init-project-bootstrap 技能比对并合并 AGENTS.md 差异，保留目标项目原有规则、命令和路径，不机械追加完整模板。无法兼容的规则列明冲突并等待用户决定，仅暂停有争议的合并部分。
- 初始化输出只报告新建、跳过、差异合并及 Git 操作结果，不输出项目业务内容。
- 初始化只建立持续开发工作流骨架，不执行具体需求开发。

## 文档规则

### 文档系统说明

- `AGENTS.md` 记录工作流、产物落点和安全规则。
- `docs/ARCHITECTURE.md` 描述系统结构、模块边界、依赖方向和关键不变量。
- `docs/PROGRESS.md` 记录项目级进度。
- `docs/requirements/index.md` 记录需求编号索引和当前状态。
- `docs/requirements/REQ-NNNN-short-title.md` 记录单个需求的澄清、设计、计划、执行状态和验证结果，`REQ-NNNN` 必须替换为实际递增编号。

### 需求文件结构

以 `docs/requirements/requirement-template.md` 为结构起点，一级标题记录需求编号和标题，以下二级章节按开发阶段补充：

- 状态：记录当前阶段和验收状态。
- 需求澄清：在完成需求澄清后，在本章节填写需求澄清结果
- 设计文档：澄清完成后，先阅读“需求澄清”章节，再记录方案与关键决策。阻碍设计的未决问题须先解决；其他遗留问题写入“未闭环事项”。
- 开发计划：澄清和设计完成后编写，按工作量划分 Stage，必要时细分 Task，并记录状态。
- 验证记录
- 验收与归档
- 未闭环事项

### 阅读规则

- 开始任何任务时先读 `AGENTS.md`。
- 涉及结构、分层、依赖或模块边界时读 `docs/ARCHITECTURE.md`。
- 涉及已有需求时先读 `docs/requirements/index.md` 和对应需求文件。
- 涉及外部依赖、框架或协议时，在对应需求文件中记录关键参考结论。
- 涉及中大改动时，先在对应需求文件的“开发计划”章节创建或更新执行计划，再开始实施。

### 写回规则

- 新需求先在 `docs/requirements/index.md` 登记编号、标题和状态。
- 同一需求的澄清、设计和计划必须写入同一个需求文件。
- 执行过程中的关键决策、验证命令和结果写回对应需求文件。
- 项目级进度记录写入 `docs/PROGRESS.md`。
- 明确未解决事项写入对应需求文件的“未闭环事项”部分。

### 执行计划状态规则

- 开发计划中的 Stage 和 Task 必须记录状态。
- 未经用户验收的需求不得标记为完成。
- 开发期间持续更新需求文件、索引状态和 `docs/PROGRESS.md`，如实记录进行中、受阻或等待验收状态。验收记录可记录未验收及反馈，只有用户验收通过后才能标记需求完成。

### 子目录 AGENTS.md 渐进披露

- 本项目约定：子目录 AGENTS.md 只描述当前目录及其子树的局部规则；可补充具体命令、路径和实现约束，不将局部要求扩展到其他目录。
- 子目录规则不得放宽根文件中的安全底线：初始化时保护已有内容、用户验收后归档，以及 Git 安全规则。根文件中明确适用于全项目的其他要求也必须保留。
- 普通局部规则在不违反根文件要求时按其明确作用域执行。规则无法同时满足时，报告具体条款、作用域和受阻动作，等待用户解决冲突；可独立进行的已授权工作继续。

## Git 安全规则

- commit message 必须遵守 Conventional Commits：feat、fix、docs、style、refactor、perf、test、build、ci、chore、revert。
- 除非用户提示，否则禁止使用 git commit --amend。
- git 操作必须串行执行，避免并发 git add、commit、merge、rebase、checkout、switch。
- 执行 git checkout、git switch 或任何会改变当前分支的操作前，必须先运行 git worktree list，并确认当前 worktree 归属和目标分支占用情况。

## Agent 交互规则

1. 首先分清用户意图，禁止将用户的所有输入都作为需求来处理。
2. 用户已提供充分信息或确认结论时，直接整理文档并继续已授权步骤；仅针对影响下一阶段的实质未决问题讨论，不重复请求已有确认。
3. 提醒审阅本身不要求暂停。用户明确要求先审核，或存在影响范围、方案或验收标准的未决决策时，等待相关确认；其他情况下按既定顺序继续已授权工作。
