# 完成进度记录器

## 执行目标
在开发收尾场景下，确保工作区干净且进度记录可审计。严格执行“只追加、不改写历史”的记录规则。

## 执行流程
1. 先读取仓库级约定文件，例如 `AGENTS.md`、`CLAUDE.md`、`README.md`、设计文档或开发计划中关于进度记录、`PROGRESS` 文件路径、条目格式、需求编号、提交记录的具体要求。
2. 若仓库对 `PROGRESS` 文件有额外要求，优先满足仓库的具体要求；本技能规则仅作为默认兜底。若仓库要求与默认格式冲突，采用仓库要求并在最终回复中简要说明。
3. 确定进度文件路径。若仓库未指定路径，默认使用 `docs/PROGRESS.md`。
4. 检查进度文件是否存在。
5. 若存在，读取全文并识别写作风格、二级章节结构、最后一条记录中的提交哈希以及已有需求编号，记最后一条哈希为 `hash1`；若不存在，则创建空文件。
6. 若仓库使用需求编号管理需求，从用户输入、开发计划、设计文档、分支名、提交信息或相关文件名中识别当前需求编号，记为 `requirement_id`。
7. 若进度文件按二级章节组织记录，先根据仓库约定、需求编号、开发计划或当前任务语义确定目标二级章节；若无法可靠确定目标章节，停止并向用户确认，禁止把记录插入任意章节。
8. 执行 `git status --porcelain` 检查工作区，并区分 `PROGRESS` 文件与其他文件的改动。
9. 若存在 `PROGRESS` 文件以外的未提交改动，必须先只提交这些改动，提交成功后获取该提交哈希，记为 `hash2`；若只有 `PROGRESS` 文件改动或工作区已干净，则将当前 `HEAD` 视为 `hash2`。
10. 生成约150字简体中文总结，内容范围仅限需求概要与开发过程中的关键决策信息：
   - 必要时参考需求澄清、设计文档或开发计划，提炼用户要解决的问题、实现边界、方案取舍与重要约束。
   - 若无需求澄清、设计文档或开发计划，则从 `hash1..hash2` 区间内提炼需求目标与关键实现决策。
   - 禁止记录通过的单元测试用例数、编译是否成功、执行过哪些验证命令、同步是否完成等过程流水账，除非这些信息本身就是需求决策或用户明确要求记录。
11. 获取当天日期（格式 `YYYY.MM.dd`）与 `hash2` 前8位短哈希，按仓库要求或默认格式构造一级列表条目。`PROGRESS` 条目中的哈希必须指向第9步得到的业务提交或既有 `HEAD`，不得指向后续提交 `PROGRESS` 文件自身产生的提交。
12. 写入或更新 `PROGRESS` 文件时，必须追加到正确位置：若没有二级章节，追加到文件末尾；若存在目标二级章节，追加到该二级章节末尾、下一个二级标题之前。禁止插入到同级历史记录中间，确保同一文件或同一二级章节内的一级列表按时间顺序递增。
13. 写入或更新 `PROGRESS` 文件后，只提交 `PROGRESS` 文件改动。该提交完成后，禁止再次修改 `PROGRESS` 文件中的哈希信息来回填 `PROGRESS` 提交自身的哈希。
14. 判断当前分支是否可以推送到远端：确认分支存在 upstream，且推送不会违反仓库约定或用户指令。若可以推送，必须在 sandbox 外执行 `git push`；若不能推送，在最终回复中说明原因。

## 默认条目格式
若仓库没有指定格式，使用以下格式：

`- ({curr_git_head_hash:8}) : {curr_date_yyyy_mm_dd} {content}`

若仓库使用需求编号管理需求，使用以下格式：

`- [{requirement_id}] ({curr_git_head_hash:8}) : {curr_date_yyyy_mm_dd} {content}`

## 内容与格式约束
- 仅使用简体中文。
- 每条记录中的 `{content}` 必须是一段连续中文文本，不使用列表、编号、小标题或多段结构。若当前上下文包含开发计划，则需要补充开发计划文件的文件名。例如 `docs/exec-plans/active/model_design.md`
- 进度文件中的记录必须保持为 Markdown 一级列表。每条记录只能以 `- ` 开头，禁止新增嵌套列表、编号列表、引用块、小标题或多级结构。
- 追加前检查进度文件全文，若发现现有内容不是一级列表，先按仓库要求处理；若仓库没有明确允许改写历史，禁止重排历史条目，只追加符合一级列表的新条目，并在最终回复中说明历史内容存在格式偏差。
- 新记录必须追加到文件末尾或对应二级章节末尾。若进度文件使用 `## ` 二级章节归档记录，只能追加到目标章节现有一级列表之后、下一个 `## ` 标题之前；若未使用二级章节，只能追加到整个文件末尾。
- 禁止为了按需求编号、提交哈希、文件名或主题分类而把新记录插入历史列表中间。一级列表的自然阅读顺序必须等同于记录产生时间顺序，越新的记录越靠后。
- 若仓库使用需求编号管理需求，每条记录必须包含需求编号。相同需求编号只能产生一个条目：若 `requirement_id` 已存在，必须更新该需求编号对应的既有一级列表条目，不得追加第二条同编号记录。
- 在更新同一需求编号的既有条目时，只允许改写该条目本身，保持其一级列表形态，并保留其他历史条目的原始顺序与内容。
- 若仓库使用需求编号但无法识别当前 `requirement_id`，停止记录并向用户询问需求编号，禁止写入无编号条目。
- 若仓库未使用需求编号，禁止修改或重排进度文件任何历史条目，只允许文件末尾追加。
- 若无法得到 `hash1`（例如首次创建文件），明确说明“基于当前提交状态生成总结”，并仍按同一格式追加（日期使用当天，格式为 `YYYY.MM.dd`）。
- `PROGRESS` 文件中的 `{curr_git_head_hash:8}` 语义是“本次需求实际改动提交”的短哈希，而不是“记录进度文件的提交”的短哈希。提交 `PROGRESS` 文件之后，不得为了让它指向最新 `HEAD` 而再次改写该条目。
- `{content}` 应像需求变更纪要，而不是验收报告。优先写“做了什么需求、为什么这样做、关键边界是什么”，不要写“跑了哪些测试、通过多少用例、构建是否成功、是否已同步或推送”等收尾操作信息。

## Git 提交约束
在需要提交时，提交信息必须满足 Conventional Commits：
- 格式：`<type>: <description>`
- `type` 仅允许：`feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert`
- `description` 至少 10 个字符，且必须具体描述技术改动
- 禁止空消息、无意义消息（如 `fix`、`update`）、禁止 `--amend`
- 当工作区同时存在 `PROGRESS` 文件和其他文件改动时，必须拆成两个提交：第一个提交不包含 `PROGRESS` 文件，第二个提交只包含 `PROGRESS` 文件。
- 生成第一个提交前必须确认暂存区不包含 `PROGRESS` 文件；生成第二个提交前必须确认暂存区只包含 `PROGRESS` 文件。

## 结果校验
执行结束后自检：
1. 工作区是否干净。
2. 进度文件是否符合仓库指定路径与仓库具体格式要求。
3. 进度文件所有记录是否均为 Markdown 一级列表。
4. 若仓库使用需求编号，当前需求编号是否只对应一个条目。
5. 若仓库未使用需求编号，进度文件是否仅新增一条记录，且该记录是否位于文件末尾或目标二级章节末尾。
6. 新记录是否符合仓库格式；若仓库未指定格式，是否符合 `- ({curr_git_head_hash:8}) : {curr_date_yyyy_mm_dd} 连续中文段落` 或 `- [{requirement_id}] ({curr_git_head_hash:8}) : {curr_date_yyyy_mm_dd} 连续中文段落`。
7. 总结是否约150字且与实际需求和关键决策一致，并且未包含测试数量、编译结果、验证命令清单、同步状态或推送状态等冗余执行信息。
8. 新记录中的哈希是否等于 `hash2` 前8位，且没有在 `PROGRESS` 提交后被改写为 `PROGRESS` 提交自身哈希。
9. 文件或目标二级章节内的一级列表是否保持时间顺序递增，没有把新记录插入历史记录中间。
10. 若分支有 upstream 且允许推送，是否已在 sandbox 外完成 `git push`；若未推送，是否已记录明确原因。

## 重试与防重
- 先构造完整候选条目字符串 `entry_line`，再执行去重检查，最后才允许写入。
- 若仓库未使用需求编号，追加前必须执行：`grep -Fqx \"$entry_line\" {progress_file}`。
- 若仓库使用需求编号，写入前必须检查 `requirement_id` 出现次数。若出现0次，追加新一级列表条目；若出现1次，更新对应条目；若超过1次，停止并向用户说明需要人工合并重复需求记录。
- 若需要追加新条目，去重通过后只能写入文件末尾或目标二级章节末尾；重试时同样必须重新定位末尾，禁止复用可能已经过期的插入行号。
- 若完整条目检查命中，说明该条目已存在，禁止再次追加；仅继续后续 `git add/commit` 或结束流程。
- 若命令在“已写入但未提交”阶段失败，重试时必须先做同样的去重检查，禁止直接再次写入。
