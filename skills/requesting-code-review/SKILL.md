# 发起代码评审

## 核心原则
早评审、常评审，把问题前移。

## 何时必须评审
- 子代理驱动开发的每个任务完成后。
- 重大功能阶段完成后。
- 合并主分支前。

## 推荐流程
1. 获取评审区间 SHA（`BASE_SHA` 与 `HEAD_SHA`）。
2. 使用 `requesting-code-review/code-reviewer.md` 模板派发评审子代理。
3. 填写：实现内容、需求来源、评审区间、简述。
4. 按严重度处理反馈：
   - Critical：立即修复
   - Important：进入下一任务前修复
   - Minor：可记录后续处理
5. 对明显不成立意见给出技术性反驳与证据。

## 与工作流集成
- 子代理开发：每个 Task 后评审。
- 执行计划：每批次或阶段后评审。
- 临时开发：合并前至少一次评审。

## 红线
- 不能因为“改动简单”跳过评审。
- 不能忽略高优先级问题继续推进。
- 不能与有效技术反馈争辩而不举证。
