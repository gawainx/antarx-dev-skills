# 测试驱动开发（TDD）

## 选择验证方式

先遵循用户和项目对 TDD 的明确要求。没有强制要求时，根据行为能否自动断言及变更风险选择；不为低影响、无行为变化的修改制造形式测试。此类修改使用对应的格式、配置或构建检查。

## RED → GREEN → REFACTOR

1. 写一个覆盖目标行为的最小测试，运行并确认它因预期行为缺失或错误而失败，而非环境或测试代码错误。
2. 做足够让测试通过的实现，不顺带扩展需求。
3. 在测试通过的状态下整理结构，重新验证受影响行为。
4. 继续下一个行为增量，完成时运行相关回归。

修复缺陷时，回归测试应能捕获原问题。接手已有实现时保留用户代码，不为重建 TDD 顺序删除实现；明确现有测试的证据范围，不伪造先失败后通过的记录。

## 测试质量

断言可观察行为，避免镜像实现细节或只证明 mock 存在。使用测试替身时保留被测行为依赖的契约和副作用。需要选择 mock 边界时阅读 `testing-anti-patterns.md`。

报告实际执行结果及未覆盖部分；不能运行测试时说明具体阻碍，不把测试文件已写好当作验证通过。
